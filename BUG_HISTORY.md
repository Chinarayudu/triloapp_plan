### [2026-10-06] Can't attach images when creating a support ticket

**Symptom**: Users and hosts couldn't add a photo (e.g. a payment screenshot) when opening or replying to a support ticket.
**Root cause**: Not a defect in existing code; the feature had never been built. Support messages were text-only (`attachments` was always `[]`), there was no upload endpoint for support, and neither app's support chat had a photo picker.
**Affected files**: backend `src/db/schema.ts` + `drizzle/0032_support_attachments.sql` (`support_messages.media_key`), `src/modules/support/support.service.ts` (upload URL, attachment checks, `attachments` with signed URLs), `support.routes.ts` (`POST /me/support/attachments/upload-url`; `mediaKey` on create/reply, text optional with a photo), `supportBot.service.ts` (transcript notes an attached photo), `supportTickets.test.ts`; `user_app_dating/src/pages/Account.jsx` + `lib/api.js`, `dating_host_app/src/screens/account.jsx` + `api/index.js` (photo button, upload, inline photos); `dateingappadminpage/src/pages/Support.tsx` (photos shown to staff); Postman User/Host.
**Fix**: Same presign-then-send flow as chat photos: the app shrinks the photo, gets an upload URL, PUTs it to S3, then sends the message with `mediaKey`. The backend checks the key belongs to the sender, the object exists, is an image and is at most 5 MB. No image moderation, since only staff see support photos.
**Call sites checked**: `listMessages` feeds the owner thread, the admin thread, `support:message` and the bot. All now get `attachments`, and the bot's transcript stays non-empty for photo-only messages. `addMessage` is used by owner, agent and bot messages; agent and bot pass no photo, so they're unchanged. Admin reply still uses `contentSchema`, which is unchanged. Full backend suite and the Postman collections pass; all three apps build.

### [2026-10-04] Cashfree Payouts dashboard "Webhook test failed. The server responded with status code 401"

**Symptom**: Adding `https://triloapp-plan.onrender.com/payments/cashfree/payout-webhook` in Cashfree Payouts → Developers → Webhooks fails the dashboard's test with `{"message":"Webhook test failed. The server responded with status code 401.","title":"REQUEST_INVALID"}`. The dashboard calls `.../cashgramuiapi/.../v1/payout/webhook/test` (`api-version: 2021-02-02`, `contentType: "JSON"`) and offers no V2 option.
**Root cause**: The account's Payouts webhooks are **V1**, which put the signature in a `signature` field in the body (HMAC-SHA256 over the other fields' values sorted by field name, Payouts client secret). Our handler only accepted **V2** (`x-webhook-signature` + `x-webhook-timestamp` headers over `timestamp + rawBody`), so every V1 request failed verification. Not a key problem: a self-signed V2 request to the deployed URL returned 200, and an unsigned one returned 401.
**Affected files**: `src/lib/payout.ts` (new `isValidPayoutWebhookV1Signature`), `src/modules/payments/cashfreeWebhook.routes.ts` (payout route parses JSON or form bodies, verifies V2 if the header is present else V1, reads `transferId`/`event` for V1 vs `data.transfer_id`/`type` for V2, and logs content type / which signature fields were present on rejection), `src/modules/payments/payouts.cashfree.test.ts`.
**Fix**: Accept both webhook versions instead of assuming V2. Settlement is unchanged — the webhook still only identifies the transfer, and `syncPayoutWithGateway` settles from Cashfree's own transfer status, so a webhook can't fake an outcome either way.
**Call sites checked**: `isValidPayoutWebhookSignature` (V2) — only the payout webhook route, behavior unchanged for V2. PG webhook (`/payments/cashfree/webhook`, PG secret) untouched. `syncPayoutWithGateway` / `getWithdrawalByPayoutTxnId` unchanged. `tsc --noEmit`; payments tests 15/15 (new: V1 JSON + form accepted, forged V1 rejected, V1 test webhook for an unknown transfer → 200); full suite 170/176 with the same 6 pre-existing test-DB-pollution failures (withdrawal policy min ₹1000, admin top-earners) as before this change.
**General lesson**: Cashfree's webhook format depends on a per-account version setting, not just the API version we call — accept every format the dashboard can send, and log enough on rejection (content type, which signature fields exist) to tell a format mismatch from a key mismatch.

### [2026-10-04] Host's video looks softer in the User app than the user's video looks in the Host app

**Symptom**: In a call, the video shown in the User app (the host's camera) looked lower quality than the video in the Host app (the user's camera).
**Root cause**: Frontend, `dating_host_app`. The host's call video always goes through the beauty pipeline (`alwaysBeautyPipeline: true`). The pipeline capped its output canvas at `MAX_PROCESS_DIM = 960`, so a 1280x720 camera went out at about 960x540. That canvas went to Agora via `createCustomVideoTrack` with no bitrate, so Agora chose its own (undocumented) one. The User app sends a plain 1280x720 camera track with `'720p_1'` (up to 1130 kbps).
**Affected files**: `dating_host_app/src/lib/beautyFilter.js` (`MAX_PROCESS_DIM` 960 → 1280, GPU/WebGL renderer only), `dating_host_app/src/lib/agora.js` (`createCustomVideoTrack` gets `bitrateMin: 600, bitrateMax: 1130`, matching `'720p_1'`).
**Fix**: The host now sends 1280x720 (720x1280 on an upright phone) at the same bitrate range as the user. 1280x720 = 921,600 px is exactly Agora's HD billing ceiling, so Agora pricing doesn't change. The Canvas2D fallback (`beautyFilterCanvas2D.js`) stays at 960; it only runs where WebGL isn't available, usually weaker devices, where the extra pixels would cost frame rate.
**Call sites checked**: every `openBeautyCamera` user. Agora calls and Agora live (`lib/agora.js`) get the higher resolution and an explicit bitrate. p2p calls (`lib/p2p.js`) and Cloudflare live (`lib/sfu.js`) get the higher resolution; both already cap the bitrate at 1.2 Mbps, so relay/SFU bytes don't change. The Go Live (`screens/live.jsx`) and beauty settings (`screens/beautySettings.jsx`) previews are sharper, at ~1.8x GPU work per frame. Audition recording (`screens/onboarding.jsx`) is recorded at 720p, so files are somewhat larger. The other `MAX_PROCESS_DIM` uses in `beautyFilter.js` (resize + the per-frame size check) read the same constant, so they stay consistent. Host app `vite build` passes. No automated frontend tests; check manually on a real call.
**Related, not fixed here**: the User app always asks for landscape `'720p_1'`, which crops and zooms the user's face on an upright phone. The Host app already uses portrait there (`callVideoEncoder()` / `cameraConstraints()`).

### [2026-10-01] Host's video frozen in the User app's call screen (audio still live)

**Symptom**: During a video call the User app showed one video stuck on a single frame, "not live", while the call carried on.
**Root cause**: Frontend bug in `dating_host_app`, not the backend. The Host app sends its camera through the beauty pipeline (`openBeautyCamera`, `src/lib/beautyFilter.js`) on every call, even with beauty off (`alwaysBeautyPipeline: true`). The video that goes out is a canvas stream, and the canvas was only redrawn from `requestAnimationFrame`. Browsers pause that whenever the page is hidden (minimized window, another tab, app switched away). So the host's outgoing video stopped on its last frame, while the mic (a separate track) kept audio live. The user's self-view is a plain camera track and isn't affected.
**Affected files**: `dating_host_app/src/lib/beautyFilter.js` (frontend repo).
**Fix**: While the page is hidden, a tiny Web Worker timer drives the same `draw()` at the normal frame interval (~31/s). Worker timers aren't paused or throttled the way page timers are. Back on screen, the worker stops and `requestAnimationFrame` takes over again. `stop()` terminates the worker and removes the visibility listener. Limit: once a phone backgrounds the app, the OS stops the camera itself, so the video still freezes there, as it would on any video app. This fix covers hidden-but-running pages (desktop browsers, a phone browser that's still on screen but not in focus).
**Call sites checked**: every `openBeautyCamera` caller. `lib/agora.js` (calls + Agora live), `lib/p2p.js` (p2p calls) and `lib/sfu.js` (Cloudflare live) now keep sending frames while hidden. The `screens/live.jsx` Go Live preview and the `screens/beautySettings.jsx` preview keep updating while hidden (small extra CPU). `screens/onboarding.jsx` audition recording keeps capturing while hidden instead of freezing. The returned API and `stop()` are unchanged. Host app `vite build` passes. There are no automated frontend tests; this needs a manual check: start a call, minimize the Host app's window, and confirm the host's video keeps moving in the User app.

### [2026-09-28] Host stuck "busy" (and user still billed) after a call's connection drops

**Symptom**: The user lost internet mid-call and both closed their apps, but the host still showed "Busy" an hour later, even after toggling online again. On the dev DB, call `9fb1918f…` was still `ongoing` after 75 minutes, with 451 billing ticks (₹1,804) and still charging the user ₹4 every 10s.
**Root cause**: "Busy" is derived from an `ongoing` call row. Nothing ended a call when a party's connection died without hanging up. The apps only call `POST /calls/:id/end` from the hang-up button. Billing runs server-side, so it kept ticking and bumping `updatedAt`, which meant the stale-call reaper (it only catches calls whose billing timer died) never touched it. The call would only have ended when the user's balance ran out. Toggling online can't help, since presence is separate from busy. This is the same pattern as the 2026-09-16 presence bug and the abandoned live-broadcast bug.
**Affected files**: `src/modules/calls/calls.service.ts` (new `endCallForLostConnection`: finds the account's ongoing call, stops billing, marks it `completed` with `endReason: "connection_lost"`, guarded on status, then `host:busy false` and `call:ended` to both), `src/realtime/socket.ts` (the disconnect handler schedules the new exported `checkAbandonedCall` after `CALL_DISCONNECT_GRACE_MS`, which does nothing if the account has reconnected), `src/config/env.ts` (`CALL_DISCONNECT_GRACE_MS`, default 20s), `vitest.config.ts` (the grace is set to never in tests, same as the live-broadcast one), `src/modules/calls/calls.socket.test.ts` (new test), `REALTIME_EVENTS.md`.
**Fix**: When either party's last socket disconnects and they haven't reconnected 20s later, end their ongoing call. The user is still billed for the time it takes to notice the drop: an immediate clean close, or up to about 45s for a dead connection (Socket.IO ping timeout), plus the 20s grace. Previously billing ran until the wallet was empty. The apps should also call `/end` themselves when the call media fails; that's a frontend follow-up.
**Call sites checked**: `endCall` (hang-up), `endCallForInsufficientBalance`, `reapStaleCalls` and `runBillingTick` are unchanged; the tick already stops itself once the call isn't `ongoing`. The status-guarded update means a hang-up and a lost-connection end at the same moment can't both apply. Accounts on two devices are only treated as gone once every socket has dropped (`isUserConnected`). Ringing calls aren't affected; they already expire after 30s. Presence, the online-session tracking and the live-broadcast auto-end share the same disconnect handler and are unchanged. `tsc` is clean and the full suite is 147/153; the 6 failures are the known 5 withdrawal tests plus the flaky admin dashboard test. The call stuck on the dev DB wasn't changed by this fix; it needs ending by hand (the permission system blocked me from writing to the shared DB).

### [2026-09-23] Admin KYC decision (and every other `/admin/*` action) crashes with a raw 500 when the admin's own account no longer exists

**Symptom**: `POST /admin/kyc/:userId/decision` (and, by the same code path, any `requireAdminPermission`-gated endpoint) returns `{"error":"Internal server error"}` even though the admin's JWT is still valid (unexpired) and the request body/target are otherwise fine.
**Root cause**: `requireAdminPermission` (`src/modules/admin/permissions.ts`) trusted a `role: "admin"` JWT outright — `if (req.user.role === "admin") { next(); return; }` — with no DB existence check, unlike the `sub_admin` branch just below it, which already looks the admin up. Downstream, `decideKyc` → `decideSubmission` writes that admin id straight into `kyc_submissions.reviewed_by_admin_id` (FK to `users.id`), and `writeAuditLog` does the same into `audit_logs.admin_id` (`NOT NULL` FK). If the admin row is gone — account deleted, or (as reproduced here) a full DB wipe — while their token is still within its TTL, the FK-constrained write throws a raw Postgres foreign-key-violation error, which isn't an `AppError`, so it falls through to the generic 500 handler instead of a clean session error.
